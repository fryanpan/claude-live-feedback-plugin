# UX Review — Markdown Review + Commenting (2026-04-18, v2)

**Reviewed:** `https://jenny-presidential-castle-hazards.trycloudflare.com/review/mvp-plan?as=bryan`
**Tool:** `claude-in-chrome` MCP (live walk, two tabs, as=bryan + as=agent)
**Viewport:** 500×599 CSS px (DPR 2). The Chrome extension wouldn't resize beyond that, so this also doubles as the sub-900px mobile-layout view.

## Goals tested

1. Open a doc, understand what it is.
2. Select text, leave a comment.
3. See the comment appear in the other user's tab live.
4. Reply to the thread from the other user.
5. Use markdown input shortcuts (`# `, `## `, `- `, `> `, `1. `).

## Goal completion

- **Open + understand:** ✅ ~1s to identify. The H1 "MVP Implementation Plan" is obvious.
- **Comment on selection:** ⚠️ **Works via direct JS selection+click — but the 💬 Comment button is literally off-screen at 500 px wide (right edge 536 px).** A real mouse user would not find it without discovering the toolbar's horizontal scroll.
- **Live sync:** ✅ Bryan tab → Agent tab: thread + reply appeared within ~400 ms.
- **Reply from other tab:** ✅ Works end-to-end.
- **Markdown input rules:** ✅ For all of `# `, `## `, `### `, `- `, `1. `, `> `. ❌ `--- ` for horizontal rule does NOT fire.

## Critical issues (block ship)

1. **Toolbar overflows; primary action clipped** — `scrollWidth 594 / clientWidth 499`. The 💬 Comment button — the whole point of the page — sits past the right edge at viewports ≤ ~580 px. On a phone or a narrow split-screen you'd never find it. Fix: wrap the toolbar onto a second row, or split formatting (left) and actions (right-docked), or collapse format icons behind a "…" overflow menu so Comment always docks right.

2. **Doc title truncated on desktop-size layouts** — `#doc-title` measures 39 px and renders `MV…`. The title flexes between Brand and the action buttons, but Copy-Bryan + Copy-Agent + user chip eat all the space. Fix: hide the two "Copy link" buttons behind an overflow menu or collapse them to icons at ≤1100 px; let the title own the middle.

3. **Floating "Comment" pill misses touch** — `floatBtn.style.display: 'none'` even with an active ProseMirror selection. The show-path is wired to the editor DOM's `mouseup`/`keyup` only; a touch long-press selection never fires those, and on mobile the OS selection UI occludes the pill anyway. Bryan already reported this ("I couldn't find the comment button on mobile"). Fix: listen to `document.selectionchange` *and* a `pointerup` with capture + read Tiptap's selection directly; on touch, dock the pill as a bottom-sheet instead of positioning it next to the caret.

## Issues (should fix before ship)

4. **Tap targets fail mobile Fitts's Law minimum** — smallest toolbar button is 25×30 px; mobile should be ≥44×44 px. Only "satisfies" the desktop 24 px floor.

5. **Visual separators don't exist** — `.format-bar .sep` has `width:1px` in CSS but the four dividers all measure 0 px; they're flex items and get collapsed. Result: `• List` and `1. List` visually read as `List1. List` (run together). Fix: `flex: 0 0 1px`.

6. **`• List` / `1. List` button labels crash into each other** — caused by #5 plus `min-width:30px` on a label that needs ~54 px. Either raise `min-width` to `auto`, add horizontal padding, or switch to icons.

7. **List/heading buttons do not scroll into view when activated** — when `H1` is already the active block and the user types to add an H2 heading below, the toolbar button state updates invisibly because it's in the overflow area.

8. **Orphaned pill position stays hidden across reloads** — after typing in the editor the floating Comment only reappears on a fresh mouse drag; keyboard-driven selection (Shift+Arrow) works once but becomes sticky-hidden once the selection straddles a comment boundary. (Needs more repro; observed once during this run.)

9. **`# `/`## ` input rules work, but `--- ` for horizontal rule does not** — minor but visible mismatch with the toolbar which exposes `—`.

10. **"Claude is active in this tab group" overlay from Chrome extension clips the thread list** — not our code, but real during Bryan's usage; worth reserving 48 px of bottom padding in the threads pane to compensate.

## Polish (post-ship OK)

- **Time format `just now` / `9m`** — good. `6m` right after an action is slightly jarring; acceptable.
- **"Copy Bryan link" / "Copy Agent link"** — labels are clear but wordy; at desktop width two identical buttons side-by-side feels bureaucratic. A single "Share…" menu with two options is cleaner.
- **Composer snippet** — starts mid-word ("mentation Plan Spec: ../../su") when the selection is arbitrary. Expanding snippet boundaries to word breaks would read cleaner.
- **Empty paragraph artifacts from my tests stayed in the doc** — Yjs + Collab's undo only cleared 3 of my 20-ish inserts. Users will hit this too any time they test input rules; exposing a "Revert last 1 minute" clean-up would help.

## What worked well

- **Live collab sync is fast and correct.** Bryan tab → Agent tab in under half a second. Thread + reply + resolve propagate as expected.
- **Toolbar active-state indicator** — `H1` is highlighted when the cursor is in the H1 title. Reassuring.
- **Markdown input rules for headings, lists, blockquote** — the most-used ones do fire, once the real `handleTextInput` path is used. My earlier belief that they were broken was wrong.
- **The fix from the last session is real** — after switching the sync-plugin key import to `@tiptap/y-tiptap`, the Comment button captures selection and opens the composer with the right snippet.

## Assessment of the `/ux-review` skill itself

Bryan asked me to evaluate the skill while using it. Findings:

**What the skill does well**
- The *checklist* is concrete. Nielsen + Fitts gave me categories I would have missed on vibe (separators, tap target sizing).
- The "Don't grade your own homework" anti-pattern is actually load-bearing: I built this UI and I *still* would have missed the off-screen Comment button without a walk — I had been touching the code from above, not from the user's cursor down.
- The "walk each goal" loop (land cold → find starting point → try to complete → try to mess it up → try mobile) forced me to simulate the Bryan-tab vs Agent-tab flow I'd otherwise have taken for granted.

**What the skill lacks / what I'd add**
- **No guidance for when the Chrome tool can't give you a representative viewport.** Mine was stuck at 500×599 — the skill should explicitly say "measure what you can in viewport X, then state which viewports remain unverified," rather than leaving the agent to improvise.
- **"Take screenshots at the key states"** is aspirational — in practice I couldn't cheaply save screenshots to disk from the MCP tool, so the report references the live walk without embedding images. The skill should either provide a saveScreenshot helper or explicitly accept that the report is text-only and list the states captured.
- **No "diff the report against the user's own complaint"** step. Bryan told me "it feels super janky" and "comment is hard to find on mobile." The skill's critical-issues output happens to cover both, but the skill could explicitly ask: "Does every user-reported complaint map to a critical/issue finding in your report? If not, your walkthrough missed something."
- **Goal completion metric is good but silent on partial failures.** A user can complete a goal by working around an off-screen button — that's "success" in the strictest sense but not user-success. I'd add a "completion quality" rating (effortless / friction / workaround-required / failed) instead of a binary check.
- **The heuristic list is long.** 10 Nielsen heuristics + Fitts + visual hierarchy + goal completion = 40+ sub-questions. For a 20-minute review I used maybe 10. A ranked subset ("first 5 to always check, rest on demand") would get the agent started faster.
